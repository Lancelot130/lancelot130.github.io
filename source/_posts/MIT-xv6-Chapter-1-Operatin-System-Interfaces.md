# MIT xv6 Chapter 1 操作系统接口

## 一、操作系统概述与接口设计

### 操作系统

操作系统的核心职责在于**在多个应用程序之间共享计算机硬件，提供比底层硬件本身更丰富、更易用的抽象服务**。概述而言，操作系统承担四大关键任务：

- 1. 硬件抽象：掩盖不同厂商与型号的磁盘、网卡、显示设备硬件差异，向应用程序提供统一、一致的抽象接口。
- 2. 资源复用与共享：在多任务环境下协调 CPU、内存与存储资源，使多个程序能够同时（或看似同时）高效运行且不发生混乱。
- 3. 隔离与安全保护：建立严格的安全保护边界，防止错误或恶意的应用程序破坏其他程序或操作系统内核自身的运行状态。
- 4. 高性能保障：确保操作系统自身提供的抽象层不会成为应用程序充分发挥硬件性能的瓶颈。

### 接口设计的权衡矛盾

操作系统的“接口”本质上就是内核向用户程序提供的一组系统调用集合。它将底层的物理硬件（如 CPU、内存、磁盘）封装抽象成应用程序可以直接调用的高层服务（如进程、文件描述符、管道）。

操作系统接口的设计充满了挑战。一方面，开发者希望接口尽可能**简单而狭窄**，这能大大降低内核实现的复杂度与出错率；另一方面，应用程序又渴望获取丰富而复杂的特性。Unix/xv6给出了解决此矛盾的典范方案：设计少量能够灵活组合的**基础机制**，从而产生极高的通用性与组合表达能力。

### 内核与用户空间架构

xv6 采用了传统的**宏内核**架构。内核是一个常驻内存并具备最高硬件特权的特殊程序。运行在用户态的应用程序被称为进程，每个进程拥有私有的指令、数据与栈内存。当进程需要请求内核服务时，通过系统调用触发硬件特权级提升，陷入内核态执行，完成后降级返回用户态。

### Shell 的本质

Shell 是一个普通的用户态程序（位于 `user/sh.c`），它从用户读取命令行输入并执行程序。Shell 并非内核的一部分，这说明了系统调用接口的强大表达力，也意味着用户可以根据需要随时替换不同的 Shell 实现。

## 二、进程与内存管理

在 xv6 中，进程是资源隔离与调度的基本单位。一个进程由用户空间内存（代码段、数据段、栈段）与内核私有状态（如进程标识符 PID、页表指针、内核栈、运行状态等）共同组成。xv6 采用**分时复用 (Time-sharing)** 机制在多个进程间透明切换 CPU。

### 分时复用是怎么工作的？

在 xv6 / Unix 操作系统中，分时复用的完整切换流程可以精简为以下 3 个步骤：

当系统中运行的进程数量超过物理 CPU 核心数时

1. **主动让出或强制切换**：当一个进程需要等待 I/O（如读写磁盘、管道或键盘输入）调用 `sleep` 时[4]，或者当定时器中断触发（该进程的时间片用完）时，内核会暂停当前进程的运行。
2. **保存状态（Save Context）**：内核将该进程当前的 CPU 寄存器（Callee-saved）、程序计数器（PC）等运行状态安全地保存到内存中。
3. **恢复并切换（Restore Context）**：内核调度器挑选下一个准备就绪的进程（进程状态为 `RUNNALBE`），恢复其之前保存的寄存器状态，让 CPU 接着执行新进程。

由于这种上下文切换速度极快，用户完全感知不到停顿，看起来就像所有程序在同时运行。

### 核心系统调用

```c
int fork();
```

创建一个新进程（子进程）。子进程拥有与父进程完全相同的内存内容（代码、数据、栈和文件描述符表）。`fork()` 在父子进程中各返回一次：在父进程中返回子 pid (>0)，在子进程中返回 0。失败时返回 -1。父子进程拥有各自独立的内存空间，后续对变量的修改互不影响。

```c
int exit(int status);
```

使当前进程停止运行并释放占用的内存、打开文件等资源。`status` 为退出状态码，习惯上 0 表示成功，非 0 表示异常或失败。进程调用 exit() 后绝不返回。

```c
int wait(int *status);
```

使父进程暂停执行，直到其某个子进程退出或被杀死。`wait()` 返回已退出子进程的 pid，并将退出状态写入 `\*status` 指向的内存。若无子进程则立即返回 -1。

```c
int exec(char *file, char *argv[]);
```

从文件系统中加载指定格式（xv6 使用 ELF 格式）的可执行文件，完全替换当前进程的内存内容（代码段、数据段、栈段），并从 ELF 头部指定的入口点开始执行。成功时 `exec()` 不返回，仅在找不到文件或格式错误等异常时返回 -1。

```c
char \*sbrk(int n);
```

在运行时动态调整进程数据段（堆内存）的大小，将其扩展或缩小 n 字节。返回新扩充内存的首地址，通常被 `malloc()` 在底层调用。

### 具体代码实现

#### fork()、wait() 与 exit() 协作模式

```c
int pid = fork();

if (pid > 0)
{
    printf("parent: child=%d\n", pid);
    pid = wait((int *) 0); // 阻塞等待子进程退出并回收资源
    printf("child %d is done\n", pid);
}
else if (pid == 0)
{
    printf("child: exiting\n");
    exit(0); // 子进程主动退出，汇报状态码 0
}
else
    printf("fork error\n");
```

#### exec() 加载新程序模式

```c
char *argv[3];
argv[0] = "echo"; argv[1] = "hello"; argv[2] = 0; // NULL 结尾数组
exec("/bin/echo", argv); // 成功时加载 ELF 程序并替换当前进程，不返回
printf("exec error\n"); // 只有 exec 执行失败（如文件不存在）时才会运行到此报错
```

### Q&A

~MIT 的学生和我的疑问以及 Rober 教授的回答~

**Q1：如果父进程有多个子进程，`wait` 是不是会在第一个子进程完成时就退出？这样的话，还有一些与父进程交错运行的子进程，是不是需要有多个wait来确保所有的子进程都完成？**

**A1：是的，如果一个进程调用 `fork` 两次，如果它想要等两个子进程都退出，它需要调用 `wait` 两次。每个 `wait` 会在一个子进程退出时立即返回。当 `wait` 返回时，你实际上没有必要知道哪个子进程退出了，但是 `wait` 返回了子进程的进程号，所以在 `wait` 返回之后，你就可以知道是哪个子进程退出了。**

**Q2：为什么将 `fork` 与 `exec` 分离？**

**A2：`fork` 和 `exec` 是分开的系统调用，意味着在子进程中有一段时间，`fork` 返回了，但是 `exec` 还没有执行，子进程仍然在运行父进程的指令。所以这段时间，尽管指令是运行在子进程中，但是这些指令仍然是父进程的指令，所以父进程仍然可以改变东西，直到代码执行到了 `exec`。这里 `fork` 和 `exec` 之间的间隔，提供了 Shell 修改文件描述符，实现重定向等功能的可能。**

## 三、 I/O 与文件描述符

文件描述符 (File Descriptor, fd) 是一个代表内核所管理 I/O 对象（普通文件、目录、设备、管道）的非负小整数。文件描述符接口将所有的 I/O 对象统一抽象为无结构的字节流 (Stream of Bytes)，抹平了底层的硬件与逻辑差异。内核为每个进程维护私有的文件描述符表，索引从 0 开始。按 Unix 传统约定：

- 0：标准输入 (Standard Input, stdin)
- 1：标准输出 (Standard Output, stdout)
- 2：标准错误 (Standard Error, stderr)

_在内部，xv6 内核使用文件描述符作为每个进程表的索引，这样每个进程都有一个从零开始的文件描述符的私有空间。_

这句话非常拗口也比较难理解，下面简要说明一下：

我们需要把这句话拆解成三个部分：数据结构、索引机制、以及所谓的“私有空间”。

### 数据结构

在 xv6 的内核代码 (`kernel/proc.h`) 中，每个进程由一个结构体 `struct proc` 表示。这个结构体里有一个非常关键的数组：

```c
// kernel/proc.h
struct proc {
// ... 其他属性 ...
struct file \*ofile[NOFILE]; // 打开文件表（Open File Table）
// ...
};
```

- `NOFILE` 通常是 16。这意味着每个进程最多能同时打开 16 个文件。
- `ofile` 是一个指针数组。它里面存的不是文件的数据，而是指向**内核全局文件表**中某个文件结构体的指针。

### 索引机制

当你调用 `fd = open(...)` 时，操作系统返回给你一个整数（比如 3）。 这句话的意思是：**这个整数 `3`，实际上就是 `ofile` 数组的下标（Index）**。

当你在用户空间调用 `write(3, "hi", 2)` 时，内核会做以下操作：

1. 找到当前进程的 `struct proc`。
2. 找到 `proc->ofile` 数组。
3. 取出 `proc->ofile[3]`。
4. 顺着这个指针找到真正的文件对象，然后写入数据。

### 私有空间

这是这句话的精髓。

假设有两个进程：**进程 A** 和 **进程 B**。

- 进程 A 打开了一个文件 `hello.txt`，系统把它的指针放在了 A 的 `ofile[3]` 位置。于是，对 A 来说，FD 3 代表 `hello.txt`。
- 进程 B 打开了一个完全不同的文件 `server.log`，系统把它的指针放在了 B 的 `ofile[3]` 位置。于是，对 B 来说，FD 3 代表 `server.log`。

**这就是“私有空间”的含义：** 虽然 A 和 B 都在使用数字 3，但因为它们查找的是各自独立的 `ofile` 数组，所以这个 3 对应的物理含义完全不同。

各进程打开的文件是相互隔离的。

### 核心 I/O 系统调用

```c
int read(int fd, char *buf, int n);
```

从 fd 当前偏移量处读取最多 n 字节到 `buf` 中，并更新文件偏移量。返回实际读取字节数，返回 0 表示已到达文件末尾 (EOF)，返回 -1 表示读取出错。

```c
int write(int fd, char *buf, int n);
```

将 `buf` 中的 n 字节写入 fd 当前偏移量处，并更新文件偏移量。返回实际写入字节数，小于 n 仅在出错时发生。

```c
int close(int fd);
```

释放文件描述符 fd，使其可被后续操作重新利用。内核分配新 fd 时总是选用未使用的最小非负整数。

```c
int open(char *file, int flags);
```

打开指定文件，常用控制位包括：`O_RDONLY` (只读)，`O_WRONLY` (只写)，`O_RDWR` (读写)，`O_CREATE` (不存在则创建)，`O_TRUNC` (截断为 0 长度)。

```c
int dup(int fd);
```

复制现有的文件描述符 fd，返回一个指向同一内核文件对象的新描述符，两者共享当前读写文件偏移量。

### 文件偏移量的共享机制

**文件的“当前读写位置（偏移量 offset）”是保存在内核这个共享的文件对象里的**，而不是保存在各自进程的清单里。每次调用 `write()` 时，内核会自动将这个共享偏移量向后推进。

虽然 `fork()` 复制了描述符表，但父子进程中对应的同一底层打开文件对象共享同一个读写偏移量。例如执行 `(echo hello; echo world) > output.txt` 父子进程的连续写入能够顺畅无缝拼接，而不会覆盖对方的写入内容。

## 四、管道机制

管道（Pipe）是作为一对文件描述符公开给进程的小型内核缓冲区，一个用于读取（`p[0]`），一个用于写入（`p[1]`）。将数据写入管道的一端使得这些数据可以从管道的另一端读取。管道为进程提供了一种通信（IPC）方式。

### 代码解析

使用连接到管道读端的标准输入来运行程序 `wc`。

```c
int p[2];
char *argv[2];
argv[0] = "wc";
argv[1] = 0;

pipe(p); // 创建管道，填充 p[0] (读端) 和 p[1] (写端)

if (fork() == 0)
{
    close(0); // 先关闭默认的读取的 fd
    dup(p[0]); // 将管道读端复制到标准的 fd 0
    close(p[0]); // 关闭不用的读端，保留 fd 0
    close(p[1]); // 关闭本来就不用的写端
    exec("/bin/wc", argv); // wc 从标准输入 (即管道) 读取数据
}
else
{
    close(p[0]); // 父进程关闭不需要的读端
    write(p[1], "hello world\n", 12); // 通过管道向重定向的标准输入写入数据
    close(p[1]); // 写入完成，关闭写端，向子进程发送 EOF 信号
}
```

一个很容易踩的坑：**一定要记得关闭不用的或用完的管道口**。

当管道中没有数据时，`read()` 会阻塞等待。内核规定：只有当所有指向管道写端的文件描述符都被关闭时，`read()` 才会返回 0（即读到 EOF）。在上述代码中，如果子进程在 `exec` 前没有关闭自身的写端 `p[1]`，即使父进程关闭了写端，管道写端的引用计数仍大于 0，这将导致 `wc` 在读取完数据后永远无法收到 EOF 信号而无限期死锁挂起（Hang）。

## 五、文件系统结构与硬链接

### 文件系统的设计目标

对于任何计算机系统来说，底层的物理磁盘本质上只是一大片被划分成固定大小的物理数据块（Blocks，如每个块 512 或 4096 字节）。磁盘只认识“读写第 n 号数据块”，它完全不知道什么是“文件名”，什么是“文件夹”。

但更上层的应用程序和人类用户渴望的是：

1. 直观易记的名字：通过路径(如 `/a/b/c.txt`)来存取数据。
2. 无结构的字节流 (Stream of Bytes)：可以按字节顺序读取，不用关心磁盘硬件的块边界。
3. 持久化保存 (Persistence)：即使电脑断电关机，数据依然安全保存在盘上。

所以，文件系统的设计目标就是在底层的“裸物理块”与上层的“文件名/树状目录”之间建立一座高效、可靠的映射桥梁。

### Inode 机制

在 Unix/xv6 的文件系统设计中，文件的元数据和文件的名字是**彻底解耦**的。

真正的文件实体由一个固定结构的 Inode 来代表。每一个 Inode 都有一个唯一的数字编号 inum (Inode Number)。**Inode 本身是没有名字的，它只记录文件的元数据（大小、类型、硬链接数等信息）以及指向磁盘数据块（记录文件实际内容）的指针**。

#### Inode 结构体包含的信息

从 `kernel/fs.h` 中，我们可以找到 dionode 结构体的定义。

```c
// On-disk inode structure
struct dinode {
  short type;           // File type
  short major;          // Major device number (T_DEVICE only)
  short minor;          // Minor device number (T_DEVICE only)
  short nlink;          // Number of links to inode in file system
  uint size;            // Size of file (bytes)
  uint addrs[NDIRECT+1];   // Data block addresses
};
```

- short type：文件类型（T_FILE 普通文件、T_DIR 目录、T_DEVICE 设备文件，为 0 表示空闲）。
- short nlink：硬链接计数（Link Count），记录有多少个文件名目录项指向该 Inode。
- uint64 size：文件的当前总字节数。
- uint addrs[...]：数据块指针数组，记录存放文件内容的物理磁盘块号（直接块与间接块）。

### 目录的本质：导航文件名表

文件本身没有名字，但我们却能在终端里看到的 `/a/b/c.txt` 这种路径和文件名，是因为它们都被装在目录里，**目录本质上也是一个文件。**

在 xv6 中，目录并不是一种特殊的数据结构，它本质上也是一个普通的 Inode （类型为 T_DIR）。目录文件中存放的数据内容，就是一排排固定格式的目录项结构体 struct dirent：

```c
struct dirent {
  ushort inum;
  char name[DIRSIZ];
};
```

每个目录项只包含两样东西：字符文件名 （name） 和 对应的 Inode 编号 （inum）。当某个目录项 inum 为 0 时，表示该槽位目前是未分配的。

每一个目录在创建时（`sys_mkdir` / `create`），内核都会自动在其内部写入两个初始目录项：**`.`** 和 **`..`** ：

**`.`** 指向**当前目录自己的 Inode 编号**。
**`..`** 指向**上一级父目录的 Inode 编号**。

### 硬链接

硬链接本质上就是在某个目录数据中，额外增加一行新的 `name inum` 映射记录，让一个新的文件名指向一个已经存在的 Inode 编号。

实例演示：`link` 创建硬链接与 `unlink` 删除文件名并断开连接关系

```c
open("a", O_CREATE|O_WRONLY); // 创建文件 a，此时 Inode 的 nlink（硬链接） = 1
link("a", "b"); // 为同一个 Inode 创建别名 b，此时 nlink 递增为 2
unlink("a"); // 移除文件名 a，nlink 递减为 1。文件数据依然完整存在，可通过 b 正常访问
```

这里可以引出一个问题，**磁盘数据到底是在何时被真正彻底释放归还的？**

当我们在命令行执行 `rm file`（底层调用 `unlink("file")`）时，操作系统并不一定立刻擦除磁盘数据。内核只有同时满足以下两个条件时，才会真正销毁数据块并清空 Inode：

1. 硬链接计数 `nlink == 0`（即磁盘上已经没有任何目录项/文件名指向这个 Inode）。
2. 内存引用计数 `ref == 0`（即系统中已经没有任何运行中的进程正打开着这个文件描述符）。

所以，利用此规则，我们可以做到创建“隐形的临时文件”。

```c
int fd = open("/tmp/tempfile", O_CREATE | O_RDWR);
unlink("/tmp/tempfile"); // 立即 unlink 掉文件名
```

- 效果 1（隐形防窃听）：从这一刻起，在终端输入 `ls /tmp` 完全看不到这个临时文件，其他进程无法通过路径找到它。
- 效果 2（防残留自动清理）：当前进程依然可以通过 `fd` 顺畅读写。一旦进程崩溃或退出，`close(fd)` 触发 `ref` 归零，内核会自动在第一时间彻底清空释放磁盘数据块，不会在磁盘上留下垃圾文件。

在 Unix 中，像 `mkdir`，`rm`，`ls` 都是独立的用户态程序。但 `cd` 必须由 Shell 自己亲自执行（`cd` 源代码内置在 _`user/sh.c`_ 中）。因为每个进程都有自己私有的“当前工作目录 （CWD）”。如果 `cd` 是独立程序，Shell 执行它时会 `fork()` 子进程，子进程调用 `chdir()` 改变的仅仅是子进程自己的 CWD，当子进程退出后，父进程 Shell 的工作目录不会产生任何改变。

### 小总结

1. 名字 ≠ 实体：文件内容保存在无名的 Inode 中，文件名只是目录里的一条导航记录。
2. 硬链接本质：同一个 Inode 在目录树里拥有多个不同的文件名导航记录（`nlink > 1`）。
3. 延迟安全释放：数据真正抹除的条件是 `nlink == 0` 并且 `ref == 0`。
4. **一切皆文件**：普通文件、目录、设备在 Unix 中被统一抽象为字节流描述符，奠定了坚实的 Unix 设计哲学基础。

## 深度解析 inode

在 xv6 和类 Unix 系统中，inode（index node，索引节点）是文件系统的灵魂。如果把文件系统比作一本书，那么“文件名”只是书名，而 **inode 才是这本书真正的正文、页码和版权页。**

理解 inode，最关键的一点是：**文件名和文件内容是完全解耦的。**

---

### 1. inode 的本质：文件的“身份证”

在磁盘上，文件并不是一个连续的整体。一个文件由两部分组成：

- 元数据（Metadata）：记录文件的属性（大小、类型、权限等）。这就是 inode。
- 数据块（Data Blocks）：记录文件的实际内容（比如你写的代码、存的图片）。

**每个文件有且仅有一个 inode**。在内核中，inode 用一个唯一的数字标识，称为 inumber。

### 2. inode 里到底存了什么？

你可以查看 xv6 源码中的 `*kernel/fs.h*`，一个典型的磁盘 inode（`struct dinode`）包含以下信息：

- **Type (文件类型)**：是普通文件、目录，还是设备文件？

- **nlink (硬链接数)**：有多少个文件名指向这个 inode。

- **Size (文件大小)**：文件共有多少个字节。

- **Addrs (数据块指针)**：这是最重要的部分。它是一个数组，记录了文件内容存放在磁盘的哪些块（blocks）上。

> 注意：inode 里面不包含文件名！ 文件名存放在“目录文件”的数据块里。这就是为什么你可以为同一个文件创建多个硬链接（不同的文件名，指向同一个 inode）。

### 3. inode 是如何找到数据的？（索引机制）

xv6 的 inode 使用了直接索引和一级间接索引的混合模式：

1. **直接索引 (Direct Blocks)**：`addrs` 数组的前 12 个元素直接存放磁盘块号。如果文件很小（小于 12×1024 字节），直接通过这些块号就能找到数据。

2. **间接索引 (Indirect Block)**：第 13 个元素指向一个“索引块”。这个块本身不存文件内容，而是存了 256 个其他的块号。

这种设计让 inode 既能快速访问小文件，又能支持足够大的大文件。

### 4. inode 的生命周期：磁盘 vs 内存

在 xv6 中，inode 存在两种形态：

- dinode (on-disk)：持久化存储在磁盘的“inode 区”。当你重启电脑，它依然在那里。

- inode (in-memory)：当内核需要操作某个文件时，会把磁盘上的 dinode 读入内存，增加一些运行时的信息（比如 `ref` 引用计数、`lock` 锁），这被称为 **active inode**。

内核维护了一个 inode cache (icache)。当你调用 `open` 时，内核去 icache 里找；找不到再从磁盘读。

### 5. 为什么需要 inode？（设计的精妙之处）

如果你理解了 inode，很多 OS 的“玄学”问题就迎刃而解了：

- **移动文件为什么快？**：在同一个分区移动文件，只是在目录里改了下文件名和 inode 的对应关系，inode 本身和数据块根本没动。

- **文件删除了，为什么空间没释放？**：如果一个文件被删除了，但还有一个进程打开着它（引用计数不为 0），或者还有硬链接指向它（nlink > 0），内核就不会删除 inode 和数据块。只有当 nlink == 0 且 ref == 0 时，文件才真正消失。

- **什么是“坏道”？**：如果存储 inode 的那个磁盘块坏了，即便数据块是好的，你也找不回文件了，因为“索引”丢了。

### 总结

- **inode = 文件属性 + 数据块位置。**

- **文件名只是 inode 的一个别名。**

- **inumber 是文件在文件系统里的真正唯一标识。**

## 六、真实世界界与设计演进

### 软件工具文化与 UNIX 接口的延续

UNIX 将**标准文件描述符**、**管道（Pipes）**以及简洁的 Shell 语法相结合，是通用软件设计上的重大突破。这种设计催生了著名的“**软件工具**”（Software Tools）文化，即鼓励通过组合简短、单一功能的程序来完成复杂任务，Shell 也因此成为了最早的脚本语言之一。这一经典的 UNIX 系统调用接口一直延续至今，广泛应用于 BSD、Linux 和 Mac OS X 等现代操作系统中。

### POSIX 标准与 xv6 的简化设计

为了统一 UNIX 接口，工业界制定了 **POSIX**（可移植操作系统接口）标准。然而，xv6 **并不是一个完全符合 POSIX 标准的系统**；为了保持教学上的简洁与清晰，它省略了诸如 `lseek` 等许多基础系统调用，且提供的部分系统调用也与标准有所差异。相比之下，现代商业级内核（如 Linux）提供了远为繁杂的系统调用与服务体系，包括网络协议栈（TCP/IP）、窗口图形系统、用户态线程以及成百上千种硬件设备驱动程序。

### “一切皆文件”的抽象模型与历史演化

UNIX 的精髓在于通过统一的“**文件名与文件描述符**”接口，将文件、目录以及硬件设备等多种不同类型的资源统一抽象起来。

**Plan 9 的扩展**：后来的 Plan 9 操作系统将这种“资源即文件”的概念进一步推广到了网络和图形系统。

**与 Multics 的对比**：UNIX 的前身 Multics 采用了截然不同的思路，将文件存储抽象为内存。然而 Multics 过度的复杂性反而促使 UNIX 的设计者（Ken Thompson 与 Dennis Ritchie）转向追求更加简单、窄而通用的接口抽象。

### 权限安全与操作系统核心原则

在安全保护方面，xv6 进行了大幅简化：它**不支持多用户概念**，也不存在用户间的数据隔离保护，所有 xv6 进程都默认以超级用户（`root`）权限运行。

---

尽管 xv6 进行了大量简化，但它所展示的核心原则——**硬件资源的分时复用（Multiplexing）**、**进程间的强隔离（Isolation）** 以及 **受控的进程间通信（IPC）**——依然是所有现代复杂操作系统构建的基石。
